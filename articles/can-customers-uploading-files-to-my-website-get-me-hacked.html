Can Customers Uploading Files to My Website Get Me Hacked?

The short answer: yes — an "attach a file" button is one of the oldest, most reliable ways attackers break into small business websites. Not because your customers do anything wrong. Because some upload buttons accept whatever file they're given, and an attacker doesn't send a photo. They send a file your server will run — and then they visit it the way you'd visit a webpage, and from there they own the site. In 2026 this exact trick was used against small business sites at scale. If a hack already happened, the response playbook covers what to do next; this is about whether your upload button is a door.

1. The scene: the button you added to be helpful

It seemed like good service. A job-application form that takes resumes. A contact form that accepts photos of the broken thing. A quote form that takes the blueprint. The button says "attach a file," the customer clicks it, the file lands in your inbox or your website's media library, and everyone moves on. Here's what that button actually is: an invitation for any stranger on the internet to put a file onto your server. Ninety-nine times out of a hundred, the file is a resume or a photo. The hundredth time, it's not. (If your form problem is junk messages pouring in rather than files, that's a different attack — spam through the form; this article is about what can arrive attached to one.)

2. What the attacker actually does (no jargon)

The attack has a boring name — "arbitrary file upload" — and a simple shape. The attacker picks a file that is secretly a program. On most small business sites that means a PHP file: the same kind of file your website itself is built from. The upload button takes it, the server stores it, and then the attacker opens it in a browser like any webpage. The file runs. It's called a webshell, and it's a remote control for your website: read your customer list, copy your database, plant spam pages, install more malware. Patchstack, which tracks WordPress attacks for a living, puts it bluntly — once this trick is fully pulled off, the attacker "can immediately gain full control of the hosting environment" (patchstack.com, 2026).

The part that should worry you: the check that was supposed to stop it usually just reads the file's name tag, not what's inside. Rename the attack file shell.php.jpg and a weak check sees "a photo" and waves it through. Spoof the file's declared type the same way. Security testers list a whole menu of these disguises — double extensions, fake content types, renamed files — all exploiting the same idea: the bouncer checks the ID the guest hands over, never looks at the face (medium.com pentesting guide, May 2025). The Wholesale Lead Capture hack of 2026 was even lazier than that: the plugin asked the attacker's own request which file types were allowed. The lock checked a key the burglar supplied (rswebsols.com via Wordfence).

3. Three times this happened in 2026 — to sites like yours

The wholesale form (February patch, June attacks). A WooCommerce plugin for wholesale lead capture had a flaw letting anyone — no login needed — upload a PHP webshell through its form. The fix came out February 20, 2026. Mass exploitation didn't start until June. Four months where the patch existed and most owners hadn't applied it. The webshells, researchers note, "can sit quietly in an uploads folder for months before anyone notices a thing" — from there an attacker can read the customer list, the order data, the wholesale pricing, or just use the server to attack someone else (benryan.com.au; rswebsols.com, 2026).

The page builder (August 2026). Elementor Pro — one of the most popular WordPress page builders — shipped an arbitrary file upload flaw, rated 9 out of 10 severity, fixed in version 4.2.2. Patchstack's warning: these flaws "are used in mass-exploit campaigns. Attackers use these to attack thousands of websites at a time, regardless of traffic size or popularity." Your traffic doesn't matter. The software does (patchstack.com, Aug 2026).

The contact form (September 2026). In late September 2026, security researchers reported a file-upload flaw in Contact Form 7 — the plugin behind millions of small business contact forms — is under active attack. Attackers place PHP backdoors where the server will execute them, and the early campaigns were explicitly targeting "e-commerce sites, membership platforms, and small business websites that rely heavily on contact forms" (webpronews.com, Sep 2026). If your site has a Contact Form 7 with a file field, check its update status now.

4. The part nobody tells you: the race is measured in hours

Patchstack's 2026 security report has a number worth sitting with: around half of high-impact WordPress vulnerabilities were exploited within 24 hours of being disclosed, and among the most heavily targeted, the median time from disclosure to attack was five hours. Meanwhile 46% of the serious flaws in premium plugins had no patch available at the time they became public (via wp-content.co, 2026). And the thing owners lean on — "my host handles security" — blocked only 12% of actively exploited WordPress vulnerabilities in Patchstack's testing. Even arbitrary file upload, the best-blocked category, was stopped only 60% of the time (patchstack.com, 2026). Your host is a helpful neighbor, not a locked door. The update button is the lock. (The full responsibility split — what your host covers and what stays yours — is worth reading next.) This is the same gap the disabled-plugin article warned about — attackers don't wait for a convenient moment.

5. The honest frame: not every upload button is dangerous

Two honest notes before the fixes. First: if your site is on Wix, Squarespace, or Shopify, the vendor runs the server and handles file uploads inside their own walls — this door is mostly their problem, not yours. The risk described here lives mainly on self-hosted sites (WordPress especially) and plugins that add upload features. Second: the danger isn't your customers. It's what the button is allowed to accept and what the server is allowed to run. A button that only accepts actual photos, stores them where the server can't execute code, and renames them on arrival is a reasonable button. A button that takes anything and drops it in a folder the server treats as live code is a door with the hinges on the outside.

6. The five fixes, in leverage order

1) Ask whether you need the button at all. The most secure upload feature is the one that doesn't exist. If the resume-upload field gets three files a year, replace it with "email your resume to…" and delete the button. No button, no door.

2) Allowlist, never blocklist. Don't tell the button "block the bad stuff" — there are infinite disguises. Tell it the only things it accepts: photos means .jpg and .png, documents means .pdf, and everything else is refused. The check should be enforced by the server, not trusted from the visitor's browser.

3) Put the files where they can't run. Uploaded files should land in a folder the web server treats as storage, not as code — ideally outside the publicly reachable website folder, or in a folder where script execution is disabled. This is the fix that turns a successful upload into a harmless file sitting in a drawer.

4) Update the plugin that owns the button. The first two cases above had patches waiting when the attacks came. The Wholesale Capture flaw was fixed four months before the attack wave — the victims were the ones who hadn't updated, and Elementor Pro's 4.2.2 fix was out before its exploitation window too. If your form plugin, page builder, or theme has an update pending, that's the lock, not a chore.

5) Check for squatters. A webshell already planted looks like an odd file in the uploads folder — a .php file where only photos should be, a strangely named file, something uploaded at 3 a.m. If you find anything you don't recognize, don't delete it yourself yet — that's evidence for your web person, and deleting the wrong thing can break the site. The detection article covers the full squatter hunt, and the reinfection article explains why unclosed upload doors are how malware returns after a cleanup.

7. What to tell your web person (the exact words)

Send them this: "I learned that file-upload buttons are a common break-in point and I want ours checked. Five asks: first, which forms or features on our site let visitors upload files — do we need all of them, and can we remove any? Second, what file types does each one accept, and is it an allowlist enforced server-side? Third, where do uploaded files get stored — can the server execute code from that folder, or is execution disabled? Fourth, is the plugin or code behind the upload button fully updated right now? Fifth, can you check the uploads folder for any files that shouldn't be there — especially PHP files where only photos or PDFs should be? No jargon in the answers — plain English." Five asks, and the helpful button stops being a door.

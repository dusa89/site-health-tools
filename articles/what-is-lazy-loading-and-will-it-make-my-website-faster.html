What Is Lazy Loading — and Will It Make My Website Faster?

There is a feature running on your website right now that you never asked for, and it is probably saving your visitors real seconds. It is called lazy loading: instead of downloading every image on a page the moment it opens, the browser waits until the visitor is about to scroll to each image. Here is what it does, the one image it must never touch, and the two-minute check that tells you whether yours is set up right.

Here is the plain-English version. When someone opens one of your pages, the browser has a choice: download all ten photos immediately, or download the two at the top and fetch the rest only when the visitor scrolls toward them. The second choice is lazy loading. It is not a plugin trick or a premium feature — it is a one-word instruction in the page code, loading="lazy", and most of the web now does it automatically. If your site runs WordPress, it has been doing it to every image since August 2020 without telling you. That is usually good news. But lazy loading has one famous way of going wrong — and the wrong version is applied to the single most important image on your page.

Your site is probably already doing it

The loading="lazy" attribute arrived in Chrome in 2019 (Chrome 76/77; Firefox 75 and Safari 15.4 followed), which made deferral a browser feature instead of a plugin job. Then, in August 2020, WordPress 5.5 switched lazy loading on by default for every image — iframe embeds joined in version 5.7. So unless someone turned it off, your pages have been holding back below-the-fold images for six years. You do not need a new plugin to get lazy loading; for most owners the only real question is whether it is configured correctly.

What does it actually buy you? Think about the photo-weight problem — your pages are heavy because of images. Lazy loading does not make any image smaller; it changes when each image downloads. The visitor's first screen arrives with only its own images fetched, so the page looks done sooner on a slow connection — the rest of the gallery waits in the wings. It is the difference between making the customer stand in line behind ten photos versus two.

The one image it must never touch

Here is the trap, and it is the reason this article exists separately from every other speed article on the site. Lazy loading is for images the visitor has not scrolled to yet. If it is applied to the image the visitor sees first — the hero banner, the big top-of-page photo — the browser defers the one image that defines how fast your page feels. Google measures that moment as Largest Contentful Paint — the dead time before anything appears, and lazy-loading the hero directly delays it.

This is not theoretical. Google Search's own Martin Splitt has walked through the failure mode: aggressive lazy-loading setups — especially older JavaScript libraries — put the real image URL in a custom data-src attribute instead of the normal src, and if the real URL is not in the src attribute, Google's crawler may not pick the image up at all. His advice: keep the hero and everything above the fold loading eagerly, give the biggest image fetchpriority="high" so the browser fetches it first, and verify what the search engine actually sees in Search Console's URL Inspection tool. The pattern that wins is simple — eager for the top, lazy for the rest.

Two implementation mistakes that cost you anyway

Lazy loading done carelessly still bills you twice. First, the images that arrive late still need reserved space. If an image has no width and height set, the page has no idea how tall it will be — so when it finally loads, the text below it jumps down the screen. That is the layout-jump problem, and late-arriving images are one of its classic triggers. The fix is one line of code your developer already knows: declare the dimensions.

Second, lazy loading is not compression. An unoptimized 4 MB photo that loads late is still a 4 MB photo — the visitor's phone still downloads all of it on a cellular connection, just a few seconds later. If you have not done the image-weight work first, lazy loading is rearranging the deck chairs: it helps the first screen, but the gallery still hurts. Do the compression first, the deferral second — they are complements, not substitutes.

The two-minute check

You do not need to read code to verify this. Two checks, in order:

1. Is your hero image lazy-loaded? Right-click your homepage's top image, open your browser's inspector (or ask your developer), and look at the image tag. If you see loading="lazy" on the hero or banner — the image a first-time visitor sees — that attribute should not be there. The fix is removing it from that one image, or setting it to loading="eager". This is the single highest-value lazy-loading edit a site owner can make, and it is worth checking because WordPress applies the default broadly.

2. Is everything below the fold actually deferred? Run our free speed test against your page. Google's own measurement runs against your homepage and shows you, in seconds, where the load time is going — including whether a long tail of gallery images is holding the page back. If the report shows the page is heavy below the fold, lazy loading ((or a misconfigured plugin fighting the browser's native version) is the place to look — and the general speed overview names the other three classic culprits if it isn't.

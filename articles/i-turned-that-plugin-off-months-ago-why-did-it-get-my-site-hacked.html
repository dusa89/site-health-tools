I Turned That Plugin Off Months Ago — Why Did It Get My Site Hacked?

Go look at your Plugins page right now. Scroll past the ones you use and you will find them: the slider you replaced last year, the booking plugin from the idea that never launched, the SEO tool your developer tried for a week. All switched off. All harmless-looking. Here is the part nobody told you: switching a plugin off does not remove it. Every file is still sitting on your server, still reachable from the public internet — and the automated scanners hammering every small-business website on earth do not care whether your plugin is on or off. They probe the files directly. That 'off' plugin is a door you forgot you left unlocked.

1. What 'deactivate' actually does (and doesn't do)

When you deactivate a plugin, WordPress does exactly one thing: it stops loading that plugin during normal page views. That is the whole of it. It does not delete the plugin's files. It does not take them off your server. It does not make them unreachable. The entire plugin — every PHP file, every script, every known weakness in it — is still sitting in your wp-content/plugins folder, exactly where it was.

And files on a web server are reachable. An attacker who knows the plugin's file paths — and they do, because plugin code is public — can request those files directly in a browser, bypassing WordPress's "is this plugin active?" question entirely. Wordfence, the company whose business is watching these attacks happen, puts it plainly in its security checklist: every plugin or theme on your website — active or inactive — is a potential entry point, and "malicious hackers frequently target known vulnerabilities in deactivated plugins that site owners forget to remove, as their code may still be publicly accessible."

One security writeup from September 2026 said it in six words every owner should memorize: "Deactivated is not removed." A dormant plugin still sits on your server, and it still runs code when it is exploited (devstars.com). The off switch is a pause button for you. For an attacker, nothing changed.

2. Why attackers love your junk drawer

You are not being targeted personally. Nobody is sitting at a desk plotting against your bakery — the why-small-sites-get-attacked article covers why attackers bother with small sites at all. The attacks are automated: botnets sweep the entire internet probing for known plugin file paths, and when they find one with a known vulnerability, they fire the exploit — a published recipe, no creativity required. A 2026 writeup on plugin vulnerabilities put the uncomfortable truth simply: a published vulnerability with public exploit code means any site still carrying that code is in the target pool, active plugin or not.

This is why "I don't use it, so it can't hurt me" is backwards. The plugin you don't use is the one you never update, never think about, and never notice when its developer stops patching it — which makes it the best target on your site, not the safest. Security guides are unanimous on the fix, and they all say the same unglamorous thing: if you are not using it, delete it — not just deactivate it (LinkedIn, 2026 prevention guide). Or shorter still: "Uninstalled plugins can't be exploited."

It is not theoretical. In the first week of October 2026, flaws in Ninja Forms and WPC Product Bundles were actively exploited to hack WordPress sites (BleepingComputer). Patching stopped further break-ins — but the security researchers stressed that updating does not clean a site that was already compromised. Prevention is the whole game here, and prevention starts in your plugins list.

3. The abandoned ones are worse

There is a second trap hiding in the same list: plugins whose developers have quietly walked away. A plugin that hasn't been updated in a year is abandoned — nobody is maintaining it, which means security holes in it will never be patched. The rule from the 2026 vulnerabilities writeup is blunt: delete it and find an alternative.

How to spot them: on your Plugins page, the "View details" link for each plugin shows its last update date. More than 12 months with no update is the danger zone. These are the plugins most likely to contain the exact vulnerabilities the botnets are scanning for — and because they are usually also deactivated ("I stopped using it ages ago"), they sit in the worst possible combination: unpatched, unmonitored, and still fully reachable.

4. The 5-minute dormant-plugin audit

Do this once, then put a monthly repeat on the calendar. It takes five minutes and closes one of the cheapest attack surfaces on the internet.

Step 1 — See what you're carrying. In your WordPress dashboard go to Plugins and use the "Inactive" filter. Count them. Most owners are surprised: five, ten, sometimes twenty plugins they forgot existed.

Step 2 — Delete, don't deactivate. For each inactive plugin, ask one question: do I use this? If the answer is no, delete it — the Delete link appears after deactivation. Wordfence's standing guidance: remove any plugin you haven't used in 30 days. If you ever need it again, the plugin directory still has it; reinstalling takes two minutes. That is not a reason to keep the files on your server for a year.

Step 3 — Check the "last updated" dates. For the plugins you keep, open each one's details and check the last update. Over a year with no update: treat it as abandoned, delete it, and find a maintained alternative.

Step 4 — Do the themes too. Same rule, same reason. Delete every inactive theme — keep your active theme plus one default backup (WordPress's own Twenty-something theme) in case something breaks. Attackers probe theme files exactly the way they probe plugin files.

Step 5 — Kill the test installs. Wordfence's checklist names these explicitly: old test WordPress installations — the staging copy from 2023, the "newsite" folder your developer left behind — get removed entirely. They are full websites with their own outdated plugins, sitting on your server, usually forgotten and never updated.

One caution while you work: deactivate-then-delete, in that order, and check the site still loads after each deletion. If a plugin turns out to be load-bearing in some way you didn't expect, reinstalling from the directory takes two minutes. The update article covers keeping what you keep patched — this audit is about shrinking the list of things that need patching in the first place.

5. What if the damage is already done?

If your site was already hacked through a dormant plugin, deleting it now closes the door but does not evict the intruder — the October 2026 Ninja Forms writeup was explicit that patching stops new break-ins but doesn't clean existing ones. Attackers routinely leave backdoors behind that survive the cleanup of the visible mess. Run through the has-my-site-already-been-hacked checklist (unknown admin users, mystery files, sudden redirects like the ones in the redirect-to-spam guide), and if anything looks wrong, follow the post-hack response order — which ends, fittingly, with deleting the dormant plugins so it can't happen the same way twice.
